# 가이드라인 원고 검사

`rules/`의 증류 규칙 중 **기계적으로 판정할 수 있는 것**을 검사합니다. 구조가 설득력 있는지, 3장의 위협과 4장의 대책이 맞물리는지 같은 판단은 이 스킬이 하지 않습니다 — `guideline-writer`를 쓰세요.

## 실행

```bash
python skills/guideline-lint/lint.py 원고.md
python skills/guideline-lint/lint.py 원고.md --genre control
python skills/guideline-lint/lint.py "docs/*.md" --quiet
python skills/guideline-lint/lint.py 원고.md --only ENDING-MIX,GRADE-GAP
python skills/guideline-lint/lint.py 원고.md --format json
```

표준 라이브러리만 씁니다. 종료 코드는 오류가 있으면 1, 없으면 0입니다.

검사 항목은 23개입니다.

장르를 생략하면 추정합니다. 신호를 보는 순서가 있습니다.

1. 행머리에 조 제목(`제4조(적용 범위)`)이 있으면 → `ordinance`
2. 경어체가 비경어체보다 많으면 → `manual`
3. **`제N절` 제목 체계가 있으면 → `guideline`**
4. 조문 인용이 20회를 넘으면 → `ordinance`
5. 통제항목 ID가 20회를 넘으면 → `control`
6. 나머지 → `guideline`

3번이 4·5번보다 앞에 있는 것이 중요합니다. **근거 법령을 성실히 인용하고 통제항목 체계까지 쓰는 분야별 가이드라인은 조문과 ID가 둘 다 많아집니다.** 시험 집필한 원고는 조문 인용 164회, 통제항목 ID 616회였고, 이 순서가 없으면 법령형 지침이나 통제항목 체계 문서로 오판됩니다.

추정이 틀리면 `--genre`로 지정하세요. **장르를 잘못 잡으면 경어체 검사가 거꾸로 동작합니다.**

**같은 성격의 지적은 하나로 묶어 횟수와 예시 줄번호만 보여줍니다.** 문서 전체에 걸친 일관성 문제를 줄마다 반복 출력하면 읽을 수 없습니다.

`EM-DASH`는 **산문 줄만 셉니다.** 표 셀의 `문서 — 자산 등록부`, 캡션의
`[표 4-8] … — 도입·구축 시`, 제목의 `### 시나리오 1 — 무선 구간 침투`는 문장을
잇는 것이 아니라 이름표를 가르는 자리입니다. 처음에는 대시가 있는 줄을 모두
세어 예제 원고에서 324줄이라고 했는데, 실제로 손볼 산문은 39줄이었습니다.

`MIDDOT`과 `LOCATION-REF`는 **인라인 코드와 따옴표 안을 보지 않습니다.** 나쁜
보기를 가리켜 설명하는 자리까지 지적하면 규칙을 적은 문서가 자기 규칙에
걸립니다 — `` `ㆍ`를 쓰지 마세요 `` 같은 문장이 그렇습니다.

## 검사는 줄 단위입니다

용어 혼용, 주기 누락, 위치 표현, 약어 반복은 **한 줄 안에서** 판정합니다. 따라서 **원고는 한 문단을 한 줄로 써야 합니다.** 폭에 맞춰 줄을 감아 두면 `정기적으로`와 `반기 1회 이상`이 다른 줄에 떨어져, 주기를 적었는데도 `PERIOD-VAGUE`가 뜹니다. 글을 검사기에 맞춰 휘게 만드는 일이 생깁니다.

이미 감긴 원고는 `guideline-writer`의 `unwrap.py`로 펼친 뒤 검사하세요.

## 결과를 읽는 법

### 오류는 고칩니다

오류는 규칙 위반이 아니라 **문서 내부의 모순**입니다. 의무 표현이 두 가지로 쓰였거나, 강화 항목의 모항목이 없거나, 등급 포함 관계가 깨진 것은 독자가 무엇을 해야 하는지 판단할 수 없게 만듭니다.

`ENDING-MIX`는 다수 쪽으로 맞추는 것이 기본이지만, **장르가 우선합니다** — 가이드라인이면 `~해야 한다`, 법령형 지침이면 `~하여야 한다`로 통일하세요. 법령 인용문 안의 `~하여야 한다`는 원문 그대로 두므로 검사에서 빠집니다.

### 경고는 판단해서 고칩니다

`CONTROL-OBLIGATION`은 통제항목 설명이 `~해야 한다`로 끝난 경우입니다. 이 장르에서 `~한다`가 이미 요구사항이므로 중복이고, 전부 그렇게 쓰면 등급 구분이 사라집니다. 다만 **본문에서 특정 통제를 강조하려고 일부러 쓴 것**이라면 그대로 두세요.

`PERIOD-VAGUE`는 코퍼스에서 102회 쓰이는 `정기적으로`를 지적합니다. **이 검사는 코퍼스를 따르지 말라는 쪽입니다** — 원본 문서들이 주기를 적지 않는 관행을 가졌지만, 주기가 없으면 이행 여부를 확인할 수 없습니다.

### 참고는 대개 그대로 둡니다

`TERM-MIX`는 같은 개념의 다른 표현이 함께 쓰인 것을 알려줍니다. 문맥이 다르면 둘 다 맞을 수 있습니다 — `사용자`와 `이용자`는 대민서비스 문맥에서 구별해 쓰는 것이 옳습니다.

`ABBR-NOINTRO`는 널리 알려진 약어(TLS, API 등)도 잡습니다. 독자층이 실무자라면 병기를 생략하는 것이 자연스러울 수 있습니다. 통제항목 ID (`PRS-MW-1`), 외부 점검항목 번호(`IA-01`), 권고·취약점 번호(`ICSA-21-315-02`) 안의 글자는 약어로 세지 않습니다.

`GRADE-COUNT`는 본문에 등급별 요구 항목 수를 적어 둔 문서에서만 동작합니다 (통제항목 10행 이상, 등급 칸이 읽히는 경우). **통제항목을 하나 더하면 본문 수치·체크리스트·대응표가 함께 밀리므로** 손으로 맞추지 말고 부록을 본문에서 생성하는 편이 안전합니다.

`HEADING-SEQ`와 `HEADING-GAP`은 **PDF에서 변환한 원고에서 자주 뜹니다.** 본문 문장이 제목으로 바뀌거나 글자가 깨져 번호가 어긋나기 때문입니다. 새로 쓰는 원고에서는 대개 실제 결함이니 보고, 변환물에서는 원본과 대조하세요.

## 발간 전에 보는 네 가지

발간 작업을 하면서 **검사를 통과했는데 틀렸던** 것들입니다.

`PLACEHOLDER`는 `(발행기관명)`·`0000-00-00`·`TODO`처럼 **발행본 24종에 한 번도
나오지 않은 꼴**만 봅니다. `○○`·`OOO`·`____`는 발행본도 예시와 양식에 쓰므로
발간 정보·문서이력 구역에서만 봅니다. `추후`·`확인 필요`·`(초안)`은 발행본이
실제로 쓰는 말이라 보지 않습니다.

`SOURCE-COUNT`는 **검사기가 외부 자료를 세어 볼 수 없다**는 한계에서 나온
검사입니다. 원고가 선행 자료의 점검항목을 98개라고 적었으나 실제는 112개였고,
원본을 받아 세어 보고서야 드러났습니다. 대신 **그 수를 단정한 문장이 가리키는
자료가 참고 자료 목록에 있는지** 봅니다. 목록에 없으면 원문을 확인한 적이
없다는 뜻입니다. 법령은 근거 법령 절에 적는 것이므로 제외합니다.

`DRAFT-NOTE`는 목차와 발간 정보에 있는 평서문을 봅니다. 그 두 구역은 표와
목록으로만 짜므로 평서문은 대개 집필용 메모입니다. 실제로 목차 끝의
"쪽번호는 조판 단계에서 붙인다…"가 발행본에 인쇄됐습니다. `※`로 시작하는
줄은 발행본의 관례이므로 보지 않습니다.

`EVIDENCE-NONE`은 연도와 수치를 함께 든 단락에 출처가 있는지만 봅니다.
**사실 확인은 하지 못합니다.** 예제 원고의 사례 네 건을 원문과 대조해 여섯
곳을 고쳤는데(원문에 없는 기간·빈도·순위를 덧붙임), 그것은 사람이 해야
합니다 — `guideline-writer` 5단계에 수칙을 적어 두었습니다.

## 같은 통제가 여러 표에 나온다

통제 하나가 **본문 표·부록 2 대응표·부록 4 조달표에 세 번** 나옵니다. 이름을
바꾸면 세 곳을 다 고쳐야 하는데 한 곳을 놓치면 읽는 사람이 다른 통제로 압니다.
`NAME-DRIFT`가 그걸 봅니다.

**파생 산출물은 더 쉽게 밀립니다.** 자가 점검 체크리스트(xlsx)와 요약본은
원고와 따로 있어서 검사기가 보지 못합니다. 실제로 세 차례 검토를 반영하는
동안 체크리스트의 문항 17개·증적 14개·등급 7개가 원고와 어긋나 있었습니다.
**원고를 고치면 파생본도 그 자리에서 다시 만드세요** — 나중에 맞추려 하면
어디가 밀렸는지 찾는 데 더 오래 걸립니다.

## 숫자 뒤 조사는 읽는 소리로 고른다

`[표 1-9]은`이 발행 전 검토에서 지적됐습니다. `9`는 '구'로 읽어 받침이 없으니
`는`입니다. 표와 그림을 백 번 넘게 가리키는 문서에서 사람이 매번 맞추기
어렵습니다.

| 끝 자리 | 읽는 소리 | 조사 |
|---|---|---|
| 1 3 6 7 8 0 | 일 삼 육 칠 팔 영 — 받침 있음 | `은` `이` `을` `과` |
| 2 4 5 9 | 이 사 오 구 — 받침 없음 | `는` `가` `를` `와` |

**`로/으로`는 예외입니다.** 받침이 ㄹ이면 `로`를 쓰므로(서울로) 1(일)·7(칠)·
8(팔)도 `로`입니다. 이걸 빼먹고 `1:1로`를 `1:1으로`로 고치라고 한 적이 있습니다.

코퍼스 24종에서 241곳을 재어 **226곳이 규칙대로**였습니다(93.8%). 발행본도
열에 한 번은 틀리므로 참고로만 알립니다.

괄호는 **통제 ID를 감쌀 때만** 봅니다 — `(PRS-SC-1)으로`는 `(PRS-SC-1)로`입니다.
`` `권장한다`(45)와 ``의 `와`는 숫자가 아니라 앞말에 붙으므로 보지 않습니다.

## 끼워 넣으면 번호가 밀린다

절 하나를 끼워 넣자 뒤 소절의 번호가 밀려 **`제1장 제3절 7.`이 가리키는 곳이
없어졌습니다.** 표 하나를 끼워 넣자 `[표 1-10]`이 두 개가 되었습니다. 둘 다
집필 중에 가장 흔한 결함이고, 조판기는 글자를 그대로 찍습니다.

`XREF`는 원고가 자기 안을 가리키는 참조를 전부 확인합니다 — `제N장 제M절 K.`,
`부록 N`, `[표 N-M]`, `[그림 N-M]`. 발행본에서 **독자가 찾아가는 자리**라서
오류로 봅니다.

원고는 `제4장 제1절 6., 제1절 7., 제3절`처럼 **한 줄에서 장을 한 번만 적고
이어 씁니다.** 뒤의 `제1절 7.`은 앞에서 명시한 장을 이어 받고, 명시한 적이
없을 때만 그 줄이 속한 장으로 봅니다.

`CAPTION-DUP`과 `CAPTION-SEQ`는 캡션 번호를 봅니다. 같은 번호가 둘이면 오류,
지면 순서와 다르면 경고입니다. **표를 중간에 끼울 때는 큰 번호부터 바꿔야**
중간에 겹치지 않습니다.

## 외부 검토에서 나온 여섯 가지

발행 전 검토자가 **손으로 찾아낸** 편집 결함들입니다. 전부 기계로 볼 수 있는
것이라 검사기가 놓친 것이 문제였습니다.

`FIGURE-FILE`은 원고가 끌어 쓰는 그림이 **파일로 있는지** 봅니다. 캡션만 보던
검사는 파일이 없어도 통과시켰고, 조판기는 없는 그림을 조용히 비워 둡니다.
발행본에 빈 자리가 남습니다.

`HEADING-DUP`은 한 절 안에 같은 소제목이 두 번 나오는 것을 봅니다. 문단을
옮기다 생기는데 조판기는 둘 다 찍습니다. 발행본 24종 가운데 5종이 `■`를,
5종이 `○`를 소제목 머리표로 씁니다.

`HISTORY-ORDER`·`HISTORY-NOOP`·`DATE-MISMATCH`는 발간 서지를 봅니다. 버전이
`0.1 → 0.2 → 0.7 → 0.6` 으로 뒤섞이거나, `보완한다→보완한다` 처럼 변경 전과
후가 같거나, 표지의 기준일과 이력의 최신 일자가 다른 것입니다. **마지막
것은 `최종 수정일` 칸을 두면 지적하지 않습니다** — 작성 기준일과 최종
수정일은 다른 날짜입니다.

`HISTORY-NOOP`이 생긴 이유가 재미있습니다. 표기 교정 도구가 이력 문장의
**'변경 전' 표현까지 바꿔** 무엇을 고쳤는지 알 수 없게 만들었습니다. 이력에
변경 전 표현을 적을 때는 백틱으로 묶으세요.

`CYCLE-SPACE`는 `연1회` 를 봅니다. 코퍼스는 띄움 20회(4종) · 붙임 11회(2종)
로 **띄움이 다수**이고 맞춤법도 띄웁니다. 붙여 쓴 발행본이 있어 참고로만
알립니다.

`ID-ABBREV`는 참고로만 알립니다. `TID-105, 110, 118`은 ID로 찾을 수 없어
풀어 쓰는 편이 낫지만, **발행본 24종 중 2종이 32회 그렇게 씁니다.** 틀린
것이 아닙니다.

## 이 저장소의 문서에는 돌리지 마세요

`lint.py`는 **발행할 가이드라인 원고**를 검사합니다. 이 저장소의 README 나
SKILL.md 에 돌리면 지적이 쏟아지는데, 대부분 장르가 달라서 나오는 것입니다.

- `HONORIFIC` — 스킬 문서의 `description:`은 비경어체가 맞습니다
- `ENDING-MIX` — 규칙을 설명하려면 `~하여야 한다`와 `~해야 한다`를 나란히
  보여 줘야 합니다
- `EM-DASH` — 코퍼스의 실무 안내서 5종도 산문 대시가 0개이니 규칙 자체는
  맞습니다. 다만 개발자용 문서가 발행본 문체를 따를 이유는 없습니다

표기 검사(`PARTICLE-SPACE`·`MONEY-SPACE`·`MIDDOT`)는 장르와 무관하게 맞으므로
저장소 문서에도 적용했습니다.

## 검사가 하지 못하는 것

- **구조**: 장·절 구성이 장르에 맞는지, 전개 축이 하나인지
- **대응**: 3장의 위협과 4장의 대책이 맞물리는지
- **등급 판단**: 어떤 항목이 어느 등급에 들어가야 옳은지 (포함 관계만 봅니다)
- **법령 인용의 정확성**: 조문 번호가 실제 조문과 맞는지. 꺾쇠·띄어쓰기 같은 표기만 봅니다. **발행된 정부 간행물의 인용도 틀릴 수 있으므로 조문 원문을 사람이 대조해야 합니다**(`rules/06-notation.md`)
- **맞춤법·띄어쓰기**: `grammar-checker`를 쓰세요 (korean-skills 원본)
- **문체 일관성 일반**: `govdoc-style`을 쓰세요

## 병합 셀에 주의

등급 검사는 통제항목 표에서 **`●` 또는 빈칸만으로 된 뒤쪽 연속 구간**을 등급 칸으로 봅니다. 머리글 위치를 쓰지 않는 이유는 `C 기밀 | S 민감 | O 공개` 머리글이 보통 병합된 소머리글 행에 있어서 본문 행의 열 위치와 맞지 않기 때문입니다.

**병합 셀이 있으면 등급 검사를 신뢰할 수 없습니다.** 그런 표에서는 `GRADE-UNREADABLE`이 뜨고 개별 항목 검사를 건너뜁니다. 원고에서는 병합 셀을 쓰지 말고 C/S/O를 세 칸으로 두세요 — 변환·검색·점검 자동화가 모두 깨집니다.
